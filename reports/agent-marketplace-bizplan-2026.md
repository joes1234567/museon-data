# AI Agent 市場平台 企劃書
### 版本 v1.3 ｜ 2026 年 6 月（Agent 供應商立場 + 合規補強修訂）

---

## 一、一句話定位

> **「企業 AI 能力協作市場——讓 agent 協作任務自動媒合、自動結算」**
>
> 任何開發者或企業的 AI 系統缺少某種能力，都能到這個市場找到能做這件事的 agent，完成後由系統自動觸發結算費用。

> **對外說法**：對投資人、客戶說「AI 能力外包市場」或「agent 協作結算平台」——付費主體是開發者或企業（預存點數），agent 執行任務時自動觸發扣款。避免說「agent 付費給 agent」引發「agent 有無法人資格」「怎麼開發票」等質疑。

---

## 二、為什麼現在是機會

### 市場空白

| 現有玩家 | 定位 | 缺口 |
|---------|------|------|
| Fetch.ai | 區塊鏈 + 去中心化 | 太技術、企業導入門檻高 |
| Google A2A | 協議標準，不是市場 | 只有接線規格，無媒合與結算 |
| LangChain Hub | 工具分享，不是交易 | 無結算機制、無媒合邏輯 |
| CrewAI | 自建 agent 團隊 | 不支援跨組織協作 |
| Zapier / Make.com | 自動化工作流程 | 人工設定流程，不支援自主媒合 |

**以上玩家都未提供「即開即用、自動媒合、自動結算」的 agent 協作交易市場。**

### 時機因素

- 全球 AI agent 數量爆炸式增長，單一 agent 能力有限，協作需求已出現
- Google A2A 協議（2025 年推出）解決了 agent 互通的技術問題
- 企業開始問：「我的 agent 能不能叫別人的 agent 幫忙做事？」
- 台灣市場競爭少，可先跑台灣再擴東南亞

## 三、核心概念說明

### 平台是什麼

「AI agent 版的 104 人力銀行」——

- **供給端（賣方）**：開發者上架 agent，標明能力與費率
- **需求端（買方）**：企業或開發者到平台找能力，下訂單付款
- **平台**：負責媒合、驗收、結算、抽成

### 一次完整交易流程

```
1. 買方遇到 AI 系統做不到的任務
         ↓
2. 上平台搜尋有這個能力的供應商 agent
         ↓
3. 系統推薦 3 個候選（依評分、價格、成功率排序）
         ↓
4. 買方下單 + 預付點數到平台保管
         ↓
5. 供應商 agent 執行任務
         ↓
6. 系統驗收（或人工仲裁）
         ↓
7. 驗收通過 → 釋放點數給供應商（扣手續費）
```

## 三甲、從 Agent 供應商立場看：值得加入嗎？

> 這是使用者直接問過的問題，也是讓整個市場成立的核心前提。如果供應商不願意來，平台沒有供給，什麼都不成立。

### 前提釐清：「agent」背後真正付出成本的是人

agent 沒有銀行帳戶、沒有法人資格。所謂「供應商 agent」，實際上是**建置並運營該 agent 的開發者或公司**。所以這個問題等於：

> **「一個已經建了 agent 的開發者，為什麼要來這個平台上架？」**

### 甜頭（供應商得到什麼）

| 甜頭 | 說明 |
|------|------|
| **零行銷成本取得客戶** | 不需自己建網站、不需跑業務，客戶主動來找 |
| **存量能力直接變現** | agent 已在跑，接外包只是多一條收入，邊際成本幾乎為零 |
| **信譽快速積累** | 每筆成交後的評分紀錄是「可攜帶的信用」，在平台內有競爭力 |
| **媒合系統幫你排序** | 平台依評分、成功率排序推薦，高品質供應商自然會曝光更多 |
| **跨組織接案** | 現有 agent 只服務自己公司，平台讓你服務任何買家 |

### 代價（供應商要承擔什麼）

| 代價 | 說明 |
|------|------|
| **手續費 10-18%** | 每筆收入被平台抽成，收入天花板被壓低 |
| **買家關係歸平台** | 交易透過平台進行，無法直接取得買家聯絡方式（防止繞台） |
| **能力曝光** | 上架等於公開你能做什麼，競爭者看得到 |
| **平台依賴風險** | 若平台倒閉或被競品取代，訂單來源消失 |

### 結論：對哪類供應商有價值？

| 供應商類型 | 值不值得上架 |
|-----------|------------|
| 已有能力但缺客戶的獨立開發者 | ✅ 高價值——零行銷成本就能收單 |
| 想測試市場需求的 AI 新創 | ✅ 高價值——平台是市場驗證管道 |
| 自建銷售管道的成熟 AI 公司 | ⚠️ 中——可作為補充收入，但不應押注主要渠道 |
| 純自用 agent（不對外服務） | ❌ 無意義 |

**從 agent 開發者立場，這個平台有實際價值——前提是 Phase 1 能先讓第一批供應商賺到錢。沒有這個前提，後面什麼都是空的。**

## 四、商業模式

### Phase 1：只有一條收入線（驗證期，前 3 個月）

> 驗證期專注驗證「有人願意付錢交易」，**不要同時驗證多種商業模式**。

| 收入類型 | 說明 | 費率 |
|---------|------|------|
| 平台手續費 | 每筆成功交易抽成 | **10%**（冷啟動期） |

其餘訂閱方案（Verified 標章、企業版、加速審核）**在 Phase 2 生態建立後再推**。

> **為什麼 10%？** Fiverr 收 20%、Upwork 收 5-20%，但它們已有成熟生態。冷啟動期直接收 20% 會讓供應商轉向自建。用 10% 換黏著度，Phase 3 再調整費率。

### Phase 2-3：完整收入架構

| 收入類型 | 說明 | 費率 |
|---------|------|------|
| 平台手續費（成熟期） | Phase 3 起調整 | 18% |
| 供應商訂閱（Verified） | 審核認證 + 優先曝光 + 爭議保障 | NT$1,500/月 |
| 企業版訂閱（Standard） | 自訂 SLA + API 串接 + 專屬客服 | NT$8,000/月 |
| 企業版訂閱（Pro） | 白標 API + 多帳號管理 | NT$25,000/月起 |
| 企業導入服務 | 幫企業盤點需求 + 媒合首批 agent | NT$20,000/次 |

### 試算前提假設（上線 12 個月後）

> 以下數字的**核心假設**：平均每筆交易 NT$1,500-2,500、平台在第 9 個月達到流動性引爆點（供應商 ≥100 家、月交易 ≥500 筆）、買方留存率 60%。

| 指標 | 保守 | 中性 | 樂觀 |
|------|------|------|------|
| 活躍供應商 | 50 | 150 | 400 |
| 月交易筆數 | 200 | 800 | 3,000 |
| 平均每筆金額 | NT$1,500 | NT$2,000 | NT$2,500 |
| 月手續費（18%） | NT$54,000 | NT$288,000 | NT$1,350,000 |
| 訂閱 + 導入服務 | NT$30,000 | NT$150,000 | NT$500,000 |
| **月營收合計** | **NT$84,000** | **NT$438,000** | **NT$1,850,000** |

### 損益平衡估算

| 月固定成本項目 | 估算 |
|-------------|------|
| 基礎設施（雲端 + DB） | NT$15,000 |
| 工程維護（兼職或創辦人自兼） | NT$30,000 |
| 客服 + 人工仲裁 | NT$40,000 |
| 行銷（社群 + 開發者活動） | NT$20,000 |
| **月固定成本合計** | **NT$105,000** |

> ⚠️ 原版 NT$75,000 漏列「工程維護人員」——客服與工程是兩個人，無法一人兼。
>
> 中性案月營收 NT$438,000 → **損益平衡約在第 6-7 個月（Phase 2 末期）達成**。

## 五、資金需求

| 階段 | 資金需求 | 用途 |
|------|---------|------|
| Phase 1（0-3 個月） | NT$5-10 萬 | 創辦人時間成本，工具費用幾乎為零 |
| Phase 2（3-6 個月） | NT$50-100 萬 | 開發費 NT$30-50 萬 + 雲端 NT$10 萬 + 行銷 NT$20 萬 |

## 六、三階段執行計畫

### Phase 1 — 驗證市場（0-3 個月）

**唯一目標**：找到 10 筆願意付費的真實交易，雙方都願意再來。

**冷啟動具體策略**

供給端（目標：前 20 個供應商）：
- [ ] 從現有開發者人脈邀請 10 人，給前 3 個月 0% 手續費優惠換黏著度
- [ ] 在台灣 AI 社群（Discord / Telegram 開發者群）發「尋找早鳥供應商」
- [ ] 自己上架 5 個現有 agent 能力當種子供給，避免空盤

需求端（目標：前 5 個企業客戶）：
- [ ] 聯繫現有客戶，問「有哪個 AI 任務現在做不到」
- [ ] 承諾 Phase 1 客戶免手續費、任何問題人工處理
- [ ] **失敗全額退款保證**：任務未完成，點數 100% 退回——消除買方「第一次試用」的心理障礙
- [ ] 每筆交易後協助買方產出「任務成效紀錄」（截圖 + 數據），作為招募下一批買方的社群佐證
- [ ] 記錄每筆需求類型，找出最高頻需求類別

**技術需求（最小可行）**

| 元件 | 工具 | 建置時間 |
|------|------|---------|
| 供應商登錄 | Google Form | 1 天 |
| 媒合 | 人工配對 | 即時 |
| 結算 | 銀行轉帳 + 記帳 | 1 天 |
| 溝通協調 | Telegram 群組 | 即時 |

**成功門檻**：10 筆付費交易 + 任務完成率 ≥ 80% + 買方回購意願評分 ≥ 7/10

**Phase 1 合規注意（銀行轉帳不等於免發票）**

Phase 1 用銀行轉帳結算，但**企業買家仍需要統一發票**。建議準備：
- 個人接案：以行號或公司身份開立收據
- 供應商：提醒其自行處理發票問題；Phase 1 協助對接，避免日後稽查糾紛

**Phase 1 核心原則：先驗證需求，不要先建系統**

---

### Phase 2 — 建立平台（3-6 個月）

**目標**：讓交易不靠人工介入可自動完成；月交易筆數達 200+

**技術架構**

```
使用者介面（Next.js + Tailwind）
         ↓
API 服務層（FastAPI / Python）
         ↓
┌──────────────────────────────────┐
│  媒合引擎  │  點數系統  │  驗收引擎  │
└──────────────────────────────────┘
         ↓
資料庫（PostgreSQL + pgvector 向量搜尋）
         ↓
Agent 通訊（REST API 為主；Google A2A 協議 SDK 作為進階選配，不強制依賴）
```

**核心功能優先級**

| 功能 | 說明 | 優先級 |
|------|------|-------|
| Agent 能力頁 | 像商品頁，顯示 agent 能做什麼、費率、評分 | P0 |
| 搜尋 + 篩選 | 依能力、價格、評分搜尋 | P0 |
| 點數充值 / 提領 | 買家充值，賣家提領，平台抽成 | P0 |
| **身份驗證 + API Key** | **agent 呼叫時驗證身份，防冒充與重播攻擊** | **P0** |
| 任務追蹤 | 任務狀態、進度、紀錄 | P1 |
| 評分系統 | 完成後雙方評分 | P1 |
| **爭議仲裁機制** | **驗收有爭議時的人工審裁流程 + 退款規則** | **P1** |
| 自動驗收 | AI 判斷任務是否完成 | P2 |

**驗收機制分類**（「通用 AI 判斷任何任務完成與否」是高風險做法）

| 任務型態 | 驗收方式 |
|---------|---------|
| 結構化輸出（回傳 JSON/報告） | Schema 驗證 |
| 生成型（文案、程式碼） | 買方確認 + 人工初審 |
| 動作型（傳送郵件、更新資料庫） | 副作用日誌 + 截圖存證 |

---

### Phase 3 — 規模化（6-12 個月）

**目標**：月交易額達 NT$100 萬，建立行業標準地位

- 開放 API，讓第三方 AI 工具接入平台
- 建立「Verified Agent」認證體系（公信力評級）
- 評估東南亞市場擴張（新加坡、馬來西亞）
- 評估鏈上結算（在生態規模夠大時才考慮，Phase 1-2 絕對不碰）

## 七、競爭優勢

### 為什麼你能做

| 優勢 | 說明 |
|------|------|
| 技術能力 | 懂 MCP、懂 agent 架構，能快速上線 Phase 1 MVP |
| 客戶資源 | 現有客戶就是第一批需求方，無需冷開發 |
| 開發者人脈 | 認識能上架 agent 的開發者，解決供給冷啟動 |
| 速度 | 中心化版本 6-8 週可上線，大廠動不了這麼快 |

### 護城河（跑起來後）

- **交易數據**：哪種能力最被需要、成功率多高——這是競品無法複製的
- **評分體系**：只有在平台交易的 agent 才有評分紀錄
- **生態網絡效應**：供應商越多 → 買家越多 → 供應商還想來

## 八、風險與對策

| 風險 | 嚴重程度 | 對策 |
|------|---------|------|
| 冷啟動：供需雙方都沒人 | **高** | 具體招募策略（見 Phase 1）+ 種子供給 + 早鳥免手續費 |
| 驗收爭議：任務算不算完成 | **高** | Phase 1 全人工仲裁；按任務型態設計分類驗收規則 |
| **法律合規：金流 / 發票 / 電子支付法** | **高** | **Phase 1 就必須確認**：電支法對非金融機構儲值有限制，B2B 應走「代收代付」模式（接綠界 / 藍新）而非自建儲值；企業買方需統一發票，Phase 1 若未先確認金流架構，任何收費行為都有法律風險，不可等 Phase 2 才處理 |
| 供應商品質差 | 中 | 先做邀請制，審核後才能上架；設 7 天觀察期 |
| **資安：agent 身份偽造 / 惡意 payload** | **中** | Phase 2 強制 API Key + 請求簽章；上架前沙箱測試 |
| **協議依賴：Google A2A 未成主流** | **中** | Phase 1 不依賴 A2A（人工媒合）；協議失敗時降級為 REST API 接入 |
| 被大廠抄 | 中 | 快速建立交易數據與評分體系；數據比技術更難複製 |
| 代幣問題 | 低 | Phase 1-2 用真實貨幣，完全不碰代幣 |

## 十一、總結

這個市場現在有技術（A2A 協議），有需求（agent 越來越多），缺的是**讓 agent 能互相找到、信任彼此、自動結算的平台**。

你有技術背景、現有客戶、開發者人脈——這是你能先跑起來的理由。

**最重要的一步不是建系統，是找到第一個願意付費的真實交易。**

**v1.1 修訂：**
1. 定位語言：改為「企業 AI 能力外包市場」
2. 競品分析：補入 Zapier / Make.com
3. 抽成策略：冷啟動期降為 10%
4. 驗收機制：三種任務型態分類驗收

**v1.3 修訂（本版）：**
1. **固定成本重估**：補入工程維護成本（NT$30,000），月固定從 NT$75,000 → NT$105,000；損益平衡從第5-6月延至第6-7月
2. **法律合規提前至 Phase 1**：電支法代收代付架構需在第一筆交易前確認，不能等 Phase 2
3. **買方冷啟動補強**：新增「失敗全額退款保證」+ 成效紀錄作為社群佐證，解決買方第一次試用心理障礙
4. **技術降風險**：Phase 2 改為 REST API 為主，A2A 作為進階選配，不強制依賴尚未成熟協議
5. **新增「Agent 供應商立場分析」章節（三甲）**：正面分析「agent 開發者為什麼要來上架」的甜頭與代價，以及哪類供應商真正有價值——這是平台供給端能否成立的核心前提
6. **Phase 1 合規補強**：明確指出銀行轉帳不等於免發票，補充企業買家統一發票處理注意事項

**v1.2 修訂：**
1. **Phase 1 商業模式簡化**：驗證期只保留一條收入線（10% 手續費），訂閱方案挪至 Phase 2，避免同時驗證多個模型
2. **冷啟動策略具體化**：供給端 + 需求端各有具體招募步驟與優惠設計
3. **新增資金需求章節**：三階段各自的資金缺口、來源建議
4. **損益平衡明確化**：中性案第 5-6 個月達損益平衡，有具體月固定成本拆解
