方案概況

定位

本規劃書回答一個具體問題：MUSEON 要擔任「軟體開發專案經理」角色，需要什麼能力、技能、工具？ 範疇聚焦在掌握開發進度、風險、產出品質，不是行銷或業務職能（那份是另一份規劃書）。 依 2026 年 PMP 考綱趨勢，約 60% 內容已轉向敏捷或混合式方法，僅 40% 為傳統瀑布式—— 代表現代 PM 職能的重心已經從「排甘特圖」轉向「跑 Sprint、管 Backlog、追 Burndown」。

🎯 誠實原則： 這份文件會把「MUSEON 現有機制可直接對應」跟「目前完全沒有、需要新建」分開標示，不假裝缺口已經補上。

Scrum / Agile 必備工具與 Artifact

📋 Product / Sprint Backlog

待辦事項清單，依優先級排序。目前 MUSEON 沒有正式 backlog，任務散落在 git commit 與對話紀錄裡。

🗂️ Kanban / Sprint Board

看板追蹤 To Do / In Progress / Done。可用 GitHub Projects 直接掛在既有 repo 上，成本最低。

📉 Burndown / Burnup Chart

追蹤剩餘工作量隨時間變化，判斷進度超前或落後。需要 backlog 有「點數」或「工時估算」才能畫。

🗣️ 每日站會摘要

「昨天做了什麼、今天要做什麼、卡在哪」。MUSEON 可用 L4 觀察者機制自動彙整成每日簡報，這塊技術上可行。

🔁 Sprint 回顧會議

每個週期結束檢討「哪裡做得好、哪裡卡住」。目前沒有固定 cadence，Breath Protocol 的週回望可以延伸涵蓋。

⚠️ 風險登錄表 + 機率-衝擊矩陣

PMP 考綱的高優先工具之一。MUSEON 目前完全沒有這個機制，是最大缺口之一。

成功指標：怎麼證明 PM 有在發揮作用

前一版最大的缺口是沒有驗收標準 —— 沒有 KPI，就無法回答「導入 PM 之後有沒有變好」。 業界現行標準是 DORA 四／五項指標（Google 研究團隊提出，已成軟體交付效能通用語言）， 搭配少量敏捷流程指標。

DORA 五項指標與 2025 業界基準

指標白話業界現況（2025）MUSEON 可否量測
部署頻率多久發一次版 僅 16.2% 達「隨時可發」；23.9% 一個月不到一次 可 git log + 部署紀錄
變更前置時間commit 到上線要多久 僅 9.4% 在 1 小時內；43.5% 超過一週 可 commit 時戳 vs 部署時戳
變更失敗率發出去後要回滾的比例 僅 16.7% 達 ≤4% 部分 需開始記錄回滾事件
失敗復原時間壞掉後多久修好 — 部分 Guardian／supervisord 有時戳可推
部署返工率發完又得補一版的比例 2025 新增指標 缺 需定義「返工」判準

建議做法：先量前兩項（部署頻率、前置時間）—— 這兩項用現有 git log 就能算，零新建成本， 且能立刻給出基準線。後三項等有回滾／事故紀錄再接。

🎯 KPI 設定原則： 先量「現在是多少」（基準線），不要一開始就設目標值。 沒有基準線的目標值是憑空想像；有了兩週基準線，目標才有意義。

AI 輔助開發如何改變估算 —— 這題直接影響報價

這是本版新增、也是對目前業務最直接相關的一節：「改用 AI 開發，工期與報價要不要調？」

⚠️ 2025 DORA 報告的關鍵發現： AI 導入會提升產出速度，但同時提高交付不穩定性。 推定原因是「量」—— AI 產出程式碼的速度，超過了審查與部署基礎設施能吸收的速度。

對報價與工期的三個實務含義

誤解實際報價該怎麼調
AI 寫程式快 N 倍，工期就砍 N 倍 只有「產碼」那段變快。審查、整合、測試、修不穩定性沒有等比例變快 砍開發工時，不砍驗收與整合工時
用歷史 velocity 推估就好 AI 生產力持續累積，估算基準每季都在漂移，舊基準會越估越不準 基準線改為逐季重算，不沿用半年前的數字
速度提升 = 品質不變 DORA 實證：吞吐量上升伴隨交付不穩定性上升 應增加驗收／回歸測試的比重，而非減少

建議的估算做法

  • 拆開報價結構：把「開發」與「整合＋驗收＋文件」分列，AI 只折抵前者
  • 基於程式碼庫分析估算，而非憑感覺 —— 再用實際交付資料持續校準
  • 不要把 velocity 當生產力指標：業界實證，一旦拿它當績效壓力，團隊會灌水點數而非真的變快
  • 本專案已有現成校準資料：鋼構案報價規則（模組基礎費 = 製作週數 × 12,000 + 驗收點數 × 5,000 × 複雜度係數）本身就把「週數」與「驗收點數」分開計價 —— 這個結構天生適合 AI 折抵，只調前者即可

評分方式

業界標準為 5×5 機率-衝擊矩陣：機率 1–5、衝擊 1–5， 風險分數 = 機率 × 衝擊（1–25）。 每一條風險必須有負責人 —— 沒有 owner 的風險登錄表等同沒有。

分級：1–6 低　8–12 中　15–25 高

建置藍圖與投入估算

前版標註「時程需另估」。本版依「1.1 FTE 兼任、AI 輔助」的實際條件給出投入區間。 採區間而非單點，因為 AI 輔助下的估算基準本身在漂移（見前節）。

階段產出人工投入完成判準
P1看板 + 首份 Backlog4–8 小時現有未結案項目全部進看板，無遺漏
P2每日摘要 + Sprint 週期6–12 小時連續 5 個工作日自動產出摘要無中斷
P3風險登錄表 + 品質閘4–6 小時本文件 R-01～R-05 全部有 owner 且每週更新

誠實缺口清單

⚠️ 下面這些不是「快完成了」，是完全沒有，需要從零建：
  • 沒有正式 Backlog / Sprint 系統 — 任務目前靠 git commit + 對話記錄拼湊
  • 沒有風險登錄表 — 高豐架構落差、霏翔報價疑慮這類「已知但未追蹤」的風險沒有集中管理
  • 沒有 Sprint cadence 定義 — 不知道多久算一個迭代週期
  • PM 角色本身在 1.1 FTE 下也是兼任，不是專職 —— 意味著「誰來當 PM」這個問題本身也要納入規劃，而不是預設 MUSEON 自動補位

下一步行動

  1. 確認範疇： MUSEON PM 職能只管軟體開發進度，還是也涵蓋業務/行銷專案？
  2. 選定看板工具： 建議 GitHub Projects（跟現有 repo 無縫接，零額外成本），或告知已有偏好工具
  3. 建立第一份 Backlog： 把目前手上未結案項目（高豐架構落差 8 項、霏翔報價查證等）轉成任務清單，作為試跑資料
  4. 定義 Sprint 週期： 建議先用 1 週試跑一輪，再依實際節奏調整
  5. 指派風險 owner： 本文件 R-01～R-05 目前皆無 owner —— 沒有負責人的風險登錄表等同沒有
  6. 開始量 DORA 前兩項： 用現有 git log 即可算出部署頻率與前置時間，先取得兩週基準線再談目標值
