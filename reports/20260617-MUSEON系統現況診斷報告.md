## 二、三大問題詳述

---

### 問題 A｜Gateway 未啟動（supervisord not running）

**前因**  
MUSEON 主閘道由 supervisord（v4.3.0，位於 `.venv/bin/supervisord`）管理，正常狀態下持續監聽 Telegram 訊息並分派 L1/L2 處理流程。

**事件**  
健檢快照確認：supervisord 未運行，連接埠 9001 拒絕連接（refused connection）。  
代表所有 Telegram 來訊目前不會被自動接收，只能靠手動 Claude Code session 處理。

**判斷**  
這是三個問題中技術上最容易修的，一行指令即可啟動，5 分鐘內恢復。  
問題本身不複雜，但它是系統對外可用性的底層基礎。其他問題全解決了，但 gateway 沒跑，等於大腦在運作、電話線斷了。

**估工**：5 分鐘，風險低，可立即執行。

---

### 問題 B｜D14 Outbound Gate 過度封鎖（block ratio 53.3%）

**前因**  
MUSEON 有一個 Outbound Gate，負責過濾系統主動發出的訊息，例如觀察報告、心脈回報、自省摘要，目的是避免 MUSEON 對使用者過度轟炸。Gate 使用 `intent × audience` 矩陣決定哪些訊息通過、哪些阻擋。

**事件（24 小時實測數字）**

| 指標 | 數值 |
|------|------|
| 總輸出嘗試 | 45 筆 |
| 被 block | 24 筆（53.3%） |
| 通過 | 17 筆 |
| 轉化（降級發送） | 4 筆 |
| 告警閾值 | 20% |

被 block 的 24 筆，全部是 `intent=owner_dm_notify`。  
這類訊息是 MUSEON 主動想傳給 Zeal 的觀察報告（例如「📋 看起來把拔最近在做...」「心脈自省回報...」）。

**根因**  
Zeal 的 chat_id（8252847174）被分類為 `audience=external_dm`，但 gate matrix 規則是 `owner_dm_notify → external_dm` = block。  
Zeal 應該被分類為 `owner_dm`，不是 `external_dm`。這是一個 audience 分類設定錯誤。

**為什麼危險**  
這是**靜默失效**——不報錯，只是 MUSEON 想說的話你永遠聽不到。  
表面上看系統正常運作，實際上 MUSEON 的自主回報通道已被自己的規則封住。系統在「假裝」對外溝通。

**兩個解法**

| 方案 | 描述 | 工時 |
|------|------|------|
| 改 audience 分類 | 將 Zeal chat_id 從 `external_dm` 升為 `owner_dm`，讓 `owner_dm_notify → owner_dm` 通過 | 30-60 分鐘 |
| 降頻策略 | 保持 block，但先確認 MUSEON 發的 24 筆是否真的有價值，再決定要不要開放 | 60-90 分鐘 |

建議先看被 block 的 24 筆內容，確認品質後再決定。

### 問題 C｜D21 Audit 工具路徑斷裂（10 個 ISSUE）

**前因**  
MUSEON 有一份「audit coverage matrix」，宣告系統的自我健檢由哪些工具負責覆蓋——包含 hook scripts 和 skill 的 SKILL.md 路徑。健檢器定期驗證這些路徑是否真實存在。

**事件**  
健檢揭露 10 個 `covered_by_tool_missing` ISSUE，代表矩陣宣告的工具根本不存在：

| 工具類型 | 缺失項目 |
|----------|----------|
| Hook script | `~/.claude/hooks/pre_commit_metric_freshness_gate.sh` |
| Hook script | `~/.claude/hooks/pre_commit_doc_value_lint_gate.sh` |
| Hook script | `~/.claude/hooks/pre_commit_caller_chain_gate.sh` |
| Skill | `~/.claude/skills/wiring-ghost-audit/SKILL.md` |
| Skill | `~/.claude/skills/x-ray/SKILL.md` |
| Skill | `~/.claude/skills/fix-verify/SKILL.md` |

**連帶影響（D23）**  
Manifest Index（D23）另外揭露 3 個 caller 路徑斷裂，包含：
- `~/.claude/hooks/session_start_metric_freshness.sh` 不存在
- `~/.claude/skills/x-ray/SKILL.md` 不存在（與 D21 重疊）
- `~/.claude/projects/-Users-ZEALCHOU/...` 舊路徑，應為 `-Users-joes-`（使用者目錄名稱變更後未同步）

**為什麼危險**  
這是三個問題裡風險最高的，因為它是「系統以為自己在自我健檢，但實際上沒有」。

矩陣宣告「我有 audit 工具覆蓋這些維度」，但工具不存在，等於 MUSEON 的免疫系統是紙做的。每次健檢報告顯示「有覆蓋」，那只是 matrix 上的文字，不是真實能力。  
這個問題在過去幾次大型審計（5/28、5/31）都有類似的型態：系統宣告自己有能力，但真實驗證時發現路徑從未接通。

**兩個解法**

| 方案 | 描述 | 工時 | 風險 |
|------|------|------|------|
| 清矩陣（快捷） | 把宣告刪掉，D21 ISSUE 歸零，但實際覆蓋度更差 | 15-20 分鐘 | 低，但只是讓問題從報表消失 |
| 補工具（完整） | 補建缺失的 hooks 和 skills，讓 audit 真正能跑 | 4-6 小時 | 中，需確認每個工具的設計意圖再實作 |

快捷方案只是報表清零，覆蓋度實際上更差。完整方案才能讓系統真正具備自我健檢能力。
