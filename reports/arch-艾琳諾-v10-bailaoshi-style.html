範圍控管

這份規劃的邊界——哪些在內、哪些刻意不做

業主在確認前最重要的一頁。明確邊界讓雙方對齊，避免上線後出現「我以為這個有包含」的落差。

第一階段刻意不做
自動獎金計算
獎金規則仍有彈性與例外，制度未完全標準化前做出來只會算錯。等制度確定後進 Phase 3 再建。
完整庫存／倉儲系統
借貨、合併提貨、盤點、臨時取貨情境仍複雜，第一階段不承諾庫存 100% 準確。先穩定提貨與點數流程。
借貨前台功能
第二次會議已確認：前台開放借貨反而鼓勵頻繁借貸，增加對帳複雜度。後台保留管理員人工調整的彈性。
完整 C 端電商
C 端消費者可預留身份與資料結構，但第一階段以 B 端經銷商提貨、儲值、審核為核心，不做 C 端完整購物流程。
容易被誤解的假設
≠
這不是 ERP
第一階段只解決經銷商提貨、點數、儲值、審核、報表與稽核。財務系統、人資、採購不在範圍內。
≠
這不是一般電商平台
雖然用購物車式操作，但核心是「提貨申請＋公司審核＋扣點」，不是 B2C 一般電商金流，消費者端刷卡購物不在第一階段。
!
提貨申請送出後，不立即扣點
第二次會議已確認：公司審核確認有貨後才扣點。送出申請 ≠ 點數已扣。這是避免無貨仍扣點的核心設計。
總結：這套系統的定位

一套讓經銷商可以自助查詢點數、送出提貨申請，公司端可進行儲值、審核、扣點、退點、出貨與報表管理的 B2B 經銷商營運系統。不是 ERP、不是電商、不是獎金系統——是讓提貨流程從 LINE 人工接單升級為系統自動化審核的第一步。

借貨合單

傑克飛現有網站維持不動，新提貨系統獨立建置，在傑克飛網站加入「前往提貨系統」按鈕跳轉。兩個系統後台不整合，各自獨立維運。

核心設計原則

借貨功能：設計在後台，不露在前台

這是第二次會議中最關鍵的一個設計決策——理由和執行方式值得說清楚。

不做的
前台開放借貨申請
提供借貨 UI → 養成習慣 → 月月大量借貨 → 對帳越來越複雜 → 糾紛增加 → 系統反而製造問題。
  • ✗ 借貸習慣固化，難以管控
  • ✗ 對帳複雜度倍增
  • ✗ 公平性爭議難處理
→
決定做的
後台保留管理員手動調整
前台無借貨入口 → 降低發生頻率 → 真的需要例外時，管理員後台人工處理 → 每筆都有稽核記錄。
  • ✓ 降低借貸行為的發生頻率
  • ✓ 例外仍可人工處理並留存記錄
  • ✓ 對帳保持簡單清晰
⚠ 若業務需求確定借貨是高頻需求，第二階段可重新評估是否開放前台功能。

系統設計的邊界：不是功能做不到，是刻意不放

借貨系統在技術上完全可以做。選擇不做是因為「有功能 = 有行為」——前台暴露入口會提高使用頻率。這次設計的原則是：讓系統引導健康的使用行為，而不是方便所有行為。

情境 A｜提貨爭議
以前：某經銷商說「我上次申請的貨沒有全到」，公司翻 LINE 記錄、查出貨單，來回確認半小時。系統上線後：打開稽核日誌，申請時間、審核人員、出貨日期一行看完。爭議 3 分鐘解決，雙方都有憑據。
情境 B｜下線管理
高級經銷商以前要靠打電話、傳訊息才知道下線的提貨狀況。系統上線後，登入就能看到組織樹，哪些人這個月還沒動、點數快見底——主動出擊的時機有了，不再只是被動等下線來問。

最大的回報不是省人力，是公司拿回對流程的掌控感

當提貨申請、點數異動、組織動態都在系統裡，公司不再靠 LINE 群組撐起一整個業務流程。有記錄、有數據、有預警——這是讓公司能繼續擴大經銷商規模的基礎，不是只省幾個小時。
