系統定位

這是什麼系統、做什麼、不做什麼

系統一句話定位
公司端管理儲值審核，經銷商自助提貨查點數，每位經銷商有自己的獨立會員商城——三層架構，從公司到最終消費者，一套系統全覆蓋。
✓ 這套系統做的
B2B 自助提貨入口
經銷商自助查點數、選產品、送出提貨申請——不再靠 LINE 傳訊
公司審核與扣點中心
儲值、審核、扣點、退點、出貨狀態——每個節點都有人負責、有稽核記錄
組織可視化（第二階段）
高階經銷商看下線動態，公司掌握長期未提貨、點數快耗盡的預警訊號
經銷商獨立會員商城（第三階段）
每位經銷商有專屬商城網址，會員透過連結進入、瀏覽下單，帳號與訂單自動歸屬該經銷商
✗ 這套系統不做的
不是 ERP
沒有完整倉儲管理、採購模組、財務帳套——這是提貨與點數系統，不是企業資源規劃
不是公開電商平台
會員商城不對外開放——消費者必須透過經銷商分享的專屬連結進入，各商城互相隔離，不做集中式市集
不自動計算獎金
獎金制度仍在調整——Phase 3 待制度確定後再建，避免讓不確定性卡住整個 MVP 進度
現況痛點

每天靠 LINE 撐起來的提貨流程，正在吃掉你的人力

這套系統針對艾琳諾目前最依賴人工、最難追蹤、最容易出錯的六個環節，進行系統性解決。

📱
提貨申請全靠 LINE 傳訊息
經銷商傳訊申請、公司人工接收、手動核對點數、通知出貨——每筆提貨最少 5 個來回，無法追蹤狀態。
💰
點數餘額人工查詢
經銷商想查點數只能問人，公司需人工回覆；儲值是否入帳、點數剩多少全靠人工核對，易出錯。
🔀
借貨合單無法管理
經銷商互相借點合單免運，私下約定後才通知公司，公平性無法驗證，月底對帳複雜度高。
🌳
組織樹不可見
高級經銷商看不到下線的提貨狀態與業績動態，只能靠電話詢問，無法主動引導下線行動。
⏰
長期未提貨無預警
哪些經銷商超過一段時間沒提貨、點數快過期，沒有系統提醒，靠記憶追蹤容易漏掉。
🔄
退貨退出流程不清
退貨、退出時的點數退還、九折回購機制全靠人工協調，流程未標準化，每次處理方式不一致。

核心商業邏輯

點數怎麼進來、怎麼扣掉、怎麼退回

三條核心規則定義整套系統的金流行為。這不只是技術設計，是跟業主確認的商業邏輯，也是後續報價和開發驗收的依據。

儲值流程
人工確認才入帳，每筆有來源記錄
1
經銷商付款（匯款 / 現場）
2
公司端 key 入儲值點數 + 來源標記
3
點數寫入經銷商錢包 + 稽核日誌
4
經銷商立即查到點數更新
核心原則：點數不可直接修改餘額，所有異動必須走交易紀錄
提貨申請流程
審核通過才扣點，不會先扣後退
1
登入 → 選產品加入購物車
2
系統即時試算所需點數
3
送出申請 → 狀態：待審核（尚未扣點）
4
公司審核確認有貨 → 系統扣點
5
出貨 / 自取 → 完成
核心原則：點數在審核通過後才扣，審核前取消不影響點數餘額
退點 / 取消邏輯
三種情境，不同的退點規則
情境 A：審核前取消
直接取消，點數未曾扣除，無需退點
情境 B：已扣點 + 未出貨
系統退點回錢包，留下退點交易紀錄與原因
情境 C：已出貨後退貨
走退貨申請流程：消費者全退、經銷商九折回購，人工至公司處理，系統記錄申請與結果
核心原則：退點不走自動，每筆人工調整必填原因，全部留稽核記錄

已確認的關鍵決策

第二次會議後，這四件事已經定案

這些不是待議項目——是已經雙方確認、直接進入規格的邊界決策。

借貨合單
前台不做借貨功能，後台保留彈性
前台介面不開放借貨/合單入口，避免養成習慣、引發更複雜的糾紛。後台可保留管理員手動調整點數的機制，應對真正需要的例外狀況。
退貨機制
消費者全退、經銷商九折回購
消費者 1 個月內全額退點。退出的經銷商，有效期 1 年以上的產品可申請九折回購，由會計人工到公司處理，系統記錄申請與結果。
傑克飛整合
現有網站保留，新系統加跳轉按鈕
傑克飛現有網站維持不動，新提貨系統獨立建置，在傑克飛網站加入「前往提貨系統」按鈕跳轉。兩個系統後台不整合，各自獨立維運。
獎金計算
Phase 3 獎金計算暫緩，待制度確定後再進
獎金分配制度目前仍在調整，Phase 3 獎金計算模組暫不列入 MVP 範圍。制度確定後再評估建置時程，確保做一次就是對的。

核心設計原則

借貨功能：設計在後台，不露在前台

這是第二次會議中最關鍵的一個設計決策——理由和執行方式值得說清楚。

不做的
前台開放借貨申請
提供借貨 UI → 養成習慣 → 月月大量借貨 → 對帳越來越複雜 → 糾紛增加 → 系統反而製造問題。
  • ✗ 借貸習慣固化，難以管控
  • ✗ 對帳複雜度倍增
  • ✗ 公平性爭議難處理
→
決定做的
後台保留管理員手動調整
前台無借貨入口 → 降低發生頻率 → 真的需要例外時，管理員後台人工處理 → 每筆都有稽核記錄。
  • ✓ 降低借貸行為的發生頻率
  • ✓ 例外仍可人工處理並留存記錄
  • ✓ 對帳保持簡單清晰
⚠ 若業務需求確定借貨是高頻需求，第二階段可重新評估是否開放前台功能。

系統設計的邊界：不是功能做不到，是刻意不放

借貨系統在技術上完全可以做。選擇不做是因為「有功能 = 有行為」——前台暴露入口會提高使用頻率。這次設計的原則是：讓系統引導健康的使用行為，而不是方便所有行為。

投資回收分析

導入後的實際回收——用數字說話

以雙層效益框架估算：第一層（人力成本節省）+ 第二層（喚醒沉睡經銷商業績增量）。單靠第一層要 24 個月回本；導入第二層後，保守情境約 6–7 個月。

⚠ 為什麼現在要做——這筆錢有一部分是「贖回主權」的代價

目前系統已使用超過 15 年，程式碼與客戶資料庫實際存放在舊工程師的環境中，公司沒有直接存取權。只要舊工程師不配合，系統隨時可能停擺。這不是「效率優化」的問題——是公司對自身業務流程失去控制的結構性風險。導入新系統的第一個回報，不是省人力，而是讓公司的資料、流程、稽核記錄完整歸還公司所有。

情境 A｜提貨爭議
以前：某經銷商說「我上次申請的貨沒有全到」，公司翻 LINE 記錄、查出貨單，來回確認半小時。系統上線後：打開稽核日誌，申請時間、審核人員、出貨日期一行看完。爭議 3 分鐘解決，雙方都有憑據。
情境 B｜下線管理
高級經銷商以前要靠打電話、傳訊息才知道下線的提貨狀況。系統上線後，登入就能看到組織樹，哪些人這個月還沒動、點數快見底——主動出擊的時機有了，不再只是被動等下線來問。

最大的回報不是省人力，是公司拿回對流程的掌控感

當提貨申請、點數異動、組織動態都在系統裡，公司不再靠 LINE 群組撐起一整個業務流程。有記錄、有數據、有預警——這是讓公司能繼續擴大經銷商規模的基礎，不是只省幾個小時。
