雙品牌 A 自助 ＋ B 自營
系統定位

雙品牌架構：A 品牌自助前台，B 品牌公司自營

系統一句話定位
A 品牌——經銷商刷玉山信用卡自動入點，自助提貨申請，公司審核扣點出貨；B 品牌——公司後台建立訂單，人工入帳，統一操盤，兩套品牌邏輯共用一套後台基礎設施。
🅰️
A 品牌（自助前台）
經銷商自助操作，玉山刷卡自動入點
→ 經銷商刷玉山信用卡 → Webhook 自動入點
→ 經銷商自主提貨申請 → 公司審核 → 確認庫存 → 扣點 → 出貨
→ 有獨立的 A 品牌經銷商前台入口
→ A 品牌消費者商城（第四階段）
🅱️
B 品牌（公司自營）
公司統一操盤，無獨立經銷商前台
→ 公司後台建立訂單 → 點數人工入帳
→ 公司確認庫存 → 扣點 → 出貨
→ 無獨立前台入口，全由公司後台操作

現況痛點

每天靠 LINE 撐起來的提貨流程，正在吃掉你的人力

這套系統針對艾琳諾目前最依賴人工、最難追蹤、最容易出錯的六個環節，進行系統性解決。

📱
提貨申請全靠 LINE 傳訊息
A 品牌經銷商傳訊申請、公司人工接收、手動核對點數、通知出貨——每筆提貨最少 5 個來回，無法追蹤狀態。
💰
點數餘額人工查詢
A/B 品牌點數分開管理，但都靠人工核對；刷卡是否入帳、點數剩多少全靠口頭確認，易出錯易漏記。
🔀
雙品牌流程混用難分清
A 品牌有刷卡自動入點需求，B 品牌走人工建單，兩套流程混在 LINE 群組裡操作，月底對帳複雜度高。
🌳
組織樹不可見
A 品牌高階經銷商看不到下線的提貨狀態與業績動態，只能靠電話詢問，無法主動引導下線行動。
⏰
長期未提貨無預警
哪些 A 品牌經銷商超過一段時間沒提貨、點數快過期，沒有系統提醒，靠記憶追蹤容易漏掉。
🔄
退貨退出流程不清
A/B 品牌退貨、退出時的點數退還、九折回購機制全靠人工協調，流程未標準化，每次處理方式不一致。

核心商業邏輯

點數怎麼進來、怎麼扣掉、怎麼退回——雙品牌分開算

四條核心規則定義整套系統的金流行為。A 品牌玉山刷卡自動入點；B 品牌人工 key 入。兩個品牌的點數絕對隔離，確認庫存後才扣點的原則兩者相同。

🔒
品牌隔離原則（最高優先）
A 品牌點數只能用於 A 品牌提貨；B 品牌點數只能用於 B 品牌。兩個品牌的點數帳戶完全獨立，不可互轉、不可混用，後台顯示時必須清楚標示品牌歸屬。

退點 / 取消邏輯
三種情境，退點退回原品牌帳戶
情境 A：審核前取消
直接取消，點數未曾扣除，無需退點；適用 A/B 品牌
情境 B：已扣點 + 未出貨
系統退點回原品牌帳戶，留下退點交易紀錄與原因；A/B 點數不互轉
情境 C：已出貨後退貨
走退貨申請流程：消費者全退、A 品牌經銷商九折回購，人工到公司處理，系統記錄申請與結果
核心原則：退點不走自動，每筆人工調整必填原因，退回原品牌帳戶，全部留稽核記錄

雙品牌隔離
A、B 品牌點數完全分開，不可互用
A 品牌點數不可用於 B 品牌，反之亦然。退點退回原品牌帳戶，不可跨品牌轉移。資料層硬隔離。
金流歸屬
所有款項進公司玉山帳戶
含 A 品牌刷卡儲值、消費者商城付款，全部進公司玉山帳戶，不直接到經銷商。公司再依規則分配。
扣點時機
庫存確認後才扣點，A/B 品牌一致
不管 A 品牌自助或 B 品牌代下，一律在審核通過且確認庫存後才實際扣點，避免超賣。
B 品牌前台
B 品牌不開放前台，全程後台代操作
B 品牌所有操作由公司人員後台代辦，不開放 B 品牌經銷商自助前台，亦無 B 品牌消費者商城。
組織可視範圍
高階可見下線：到下一個 52% 職等為止
同階截斷規則確認，高階經銷商看到自己授權範圍，遇到同等級自動截止，不看對方的下線。
退貨退點
1 個月內保證退 / 9 折回購 / 換品機制
1 個月內保證退換點；A 品牌退出經銷商，有效期 1 年以上產品可 9 折回購；系統記錄，人工處理。
借貸管理
前台不開放借貸，後台保留人工調整
前台不提供借點/合單入口，避免養成習慣。真的需要例外時，管理員後台人工處理，每筆留稽核紀錄。
尚待確認
B 品牌等級規則細節
A 品牌已確認 52%/48%/40%/30%，B 品牌獨立等級規則待制度化。確認後影響 M02 設定範圍。

核心設計原則

借貨功能：設計在後台，不露在前台

這是最關鍵的一個設計決策——理由和執行方式值得說清楚。

不做的
前台開放借貸申請
提供借貸 UI → 養成習慣 → 月月大量借貸 → 對帳越來越複雜 → 糾紛增加 → 系統反而製造問題。
  • ✗ 借貸習慣固化，難以管控
  • ✗ 對帳複雜度倍增
  • ✗ 公平性爭議難處理
→
決定做的
後台保留管理員手動調整
前台無借貸入口 → 降低發生頻率 → 真的需要例外時，管理員後台人工處理 → 每筆都有稽核記錄。
  • ✓ 降低借貸行為的發生頻率
  • ✓ 例外仍可人工處理並留存記錄
  • ✓ 對帳保持簡單清晰

系統設計的邊界：不是功能做不到，是刻意不放

選擇不做是因為「有功能 = 有行為」——前台暴露入口會提高使用頻率。這次設計的原則是：讓系統引導健康的使用行為，而不是方便所有行為。

投資回收分析

導入後的實際回收——用數字說話

以雙層效益框架估算：第一層（人力成本節省）+ 第二層（喚醒沉睡經銷商業績增量），以 Phase 1+2+3 投資 NT$927,350 估算。單靠第一層要 29 個月回本；導入第二層後，保守情境約 7–8 個月。

現在的日常，其實是這樣的

晚上八九點，LINE 還在跳——經銷商問「我點數到了沒」「今天出貨了嗎」，得停下手邊的事去翻對話紀錄核對。月底對帳那幾天，Excel 開好幾個分頁比對誰儲值了多少、誰的點數還沒扣，一個疏漏就是一通不好交代的電話。這些不是「效率不夠」，是每天真實在磨你跟團隊的時間和精神——接下來的數字，就是在還這筆帳。

⚠ 為什麼現在要做——這筆錢有一部分是「贖回主權」的代價

目前系統已使用超過 15 年，程式碼與客戶資料庫實際存放在舊工程師的環境中，公司沒有直接存取權。只要舊工程師不配合，系統隨時可能停擺。這不是「效率優化」的問題——是公司對自身業務流程失去控制的結構性風險。導入新系統的第一個回報，不是省人力，而是讓公司的資料、流程、稽核記錄完整歸還公司所有。

最大的回報不是省人力，是公司拿回對流程的掌控感

當提貨申請、點數異動、組織動態都在系統裡，公司不再靠 LINE 群組撐起一整個業務流程。有記錄、有數據、有預警——這是讓公司能繼續擴大經銷商規模的基礎，不是只省幾個小時。

風險與對策

12 項主要風險，附等級與對策

雙品牌架構新增多項風險，預先看到比事後補救便宜。

風險項目 等級 說明 對策
多品牌資料混淆 高 A、B 品牌資料若設計時未硬隔離，點數、訂單、報表可能跨品牌混用，導致財務混亂。 資料庫層強制品牌 ID 欄位，所有查詢預設加品牌過濾條件。P1 驗收前必跑跨品牌資料洩漏測試。
經銷商接受度低 高 部分年長或習慣 LINE 的 A 品牌經銷商可能抗拒切換到新系統，初期使用率不足。 P2 上線時並行運行（LINE + 系統），給 1–2 個月過渡期。高階經銷商先帶頭使用，帶動下線效果最好。
B 品牌代操作稽核 高 公司人員後台代辦 B 品牌所有事務，若稽核不完整，容易出現內部誤操作或爭議。 B 品牌所有代操作必須留下操作人員姓名與原因，敏感操作（大額點數調整）需主管確認，稽核不可刪除。
玉山金流串接延遲 中 玉山 API 申請有審核流程，可能比預期晚 1–2 週到位，影響 P2 開放時程。 P1 完成後立即啟動玉山申請。P2 前期先用後台人工入點作為備援，金流串接完成後自動切換。
庫存批次複雜度 中 批號/效期管理比一般庫存複雜，A/B 共倉時若批次邏輯設計不當，工時可能超估 30%。 P1 庫存模組設計階段先確認批次管理規則細節，工時預留緩衝。驗收前跑批次扣庫壓力測試。
點數異動爭議移轉 中 導入初期舊 LINE 記錄與新系統數據不一致，可能引發經銷商追溯歷史糾紛。 設定系統上線日作為數據起算點，上線前歷史交易維持現有方式處理，系統不承接歷史對帳。
退貨/退出 SOP 未完整 中 退貨流程（九折回購、點數退還）尚未完整 SOP 化，上線後容易出現漏洞。 P1 開始前確認退貨完整 SOP，寫入系統規則。退出的點數現金/轉讓由管理員人工處理，系統只記錄。
B 品牌等級規則未定 中 B 品牌獨立等級規則尚未制度化，影響 M02 品牌管理模組的設計範圍，工時有浮動。 P1 啟動前確認 B 品牌等級規則細節，確認後鎖定 M02 設計。規則越複雜，工時越高。
舊資料匯入範疇 中 舊系統資料是否需匯入、匯入量和格式，影響 P1 手動建入或 P3 AI 輔助的工時估算。 確認匯入需求後，P1 評估手動建入工時（若少量）或保留給 P3 AI 匯入（若大量）。
等級自動升級邊界 低 A 品牌等級條件已確認，但 P2 設計時若業務規則有微調，等級升降邏輯可能需重測。 P2 開發前再次確認升等條件，鎖定後才進詳細設計。降等保護規則一併確認。
AI 匯入品質 低 AI 清洗結果需人工確認，若舊資料格式混亂，確認工作量可能比預期大。 P3 啟動前先看舊資料樣本，評估清洗難度。AI 只輔助，人工確認是最後關卡。
Phase 3 範圍膨脹 低 消費者商城和 AI 匯入需求可能比預期複雜，影響 P3 建置時程。 P3 簽約時單獨評估工時與費用，視需求複雜度彈性報價，不影響 P1–2 進度。
